winds: C++ Compiler Manual

winds is a lightweight, high-performance C++ compiler targeting x86_64 Linux. It is implemented in strict C11 with zero external LLVM dependencies and generates native System V AMD64 assembly directly.

Navigation: Overview | Benchmarks | Installation | Compiler Options | Language Reference | Architecture & IR | FAQ | GitHub Repository

1. Overview

winds is designed to offer fast compilation latencies and minimal resource consumption. Unlike modern LLVM or GCC distributions that require hundreds of megabytes in toolchain binaries and shared libraries, winds is a compact single executable (~325 KB) with sub-millisecond translation speed.

Key design characteristics:

  • Zero LLVM dependencies: Fully independent frontend, type checker, intermediate representation, and machine code generator. Links against glibc only.
  • Arena-based allocation: Internal memory is allocated in 64 KB linear blocks with bump pointers, avoiding heap fragmentation and allowing instant process tear-down.
  • String interning: All identifiers and keywords are converted to unique interned pointers via 32-bit FNV-1a hashing, reducing symbol comparisons to pointer equality checks.
  • System V AMD64 compliance: Emits standard GNU Assembler (GAS) syntax adhering to standard 16-byte stack frame alignment and parameter register conventions (%rdi, %rsi, %rdx, %rcx, %r8, %r9).

3. Installation & Building

Building winds requires standard tools: a C11 compiler (GCC or Clang) and the standard GNU assembler (as) and linker (ld or gcc).

Building from Source

git clone https://github.com/don2e4/winds.git
cd winds
make

System Installation

To install globally for the current user (into ~/.local/bin, accessible anywhere in your shell): 

make install

To install system-wide (into /usr/local/bin): 

sudo make install PREFIX=/usr/local

Running the Test Suite

make test

Basic Compilation Example

Once installed, winds can be invoked anywhere in the filesystem without specifying directory prefixes:

winds program.cpp -o program
./program

4. Compiler Options

winds provides standard command-line flags compatible with conventional Unix build chains:

Option Description Default
-o <file> Write executable or object output to <file>. a.out (or input base name)
-S Compile to GNU x86_64 assembly (.s) and stop. Produces final executable
-c Compile and assemble to object file (.o), do not link. Produces final executable
-O0 Disable intermediate representation optimization passes. -O1
-O1, -O2 Enable constant folding, dead-code elimination, and jump cleanup. Enabled by default (-O1)
--emit-ast Dump Abstract Syntax Tree to standard output. Disabled
--emit-ir Dump Linear 3-Address Code (3AC) intermediate representation. Disabled
-v, --verbose Print verbose pipeline execution details and timings. Disabled
--help Display help message and exit. -
--version Display compiler version and target architecture. -

5. Language Reference

winds supports core C++ features with strict type checking, class layout computation, and scope resolution.

5.1 Classes, Structs & Member Functions

Classes support public, private, and protected access control. Methods receive an implicit this pointer as their first parameter. 

class Point {
private:
    int x;
    int y;
public:
    Point(int px, int py) {
        this->x = px;
        this->y = py;
    }

    int getX() {
        return this->x;
    }

    int getY() {
        return this->y;
    }
};

5.2 Constructors, Destructors & RAII

Constructors initialize object instances on the stack or heap. Destructors (~ClassName()) are executed automatically in reverse declaration order when stack variables leave their enclosing scope block. 

int g_cleanup = 0;

class Tracker {
public:
    Tracker() { }
    ~Tracker() {
        g_cleanup = g_cleanup + 1;
    }
};

void testScope() {
    Tracker t;
    // ...
    // t.~Tracker() is invoked automatically before testScope returns
}

5.3 Dynamic Memory (new & delete)

The new operator determines type size, calls malloc, and invokes the constructor. The delete operator calls the object destructor and releases heap memory via free. 

class Box {
public:
    int size;
    Box(int s) {
        this->size = s;
    }
};

void run() {
    Box* b = new Box(64);
    int s = b->size;
    delete b;
}

5.4 Namespaces and Scope Resolution (::)

Namespaces prevent symbol name collisions. Nested namespaces and using namespace directives are fully supported. 

namespace Math {
    int square(int v) {
        return v * v;
    }
}

int main() {
    int a = Math::square(5); // 25
    using namespace Math;
    int b = square(6);       // 36
    return a + b;            // 61
}

5.5 Function Overloading & Name Mangling

Functions and methods sharing the same identifier are disambiguated by argument count and types. Symbols are encoded with a _W_ prefix to ensure valid assembler labels. 

int add(int a, int b) {
    return a + b;
}

int add(int a, int b, int c) {
    return a + b + c;
}

int main() {
    int x = add(10, 20);     // calls _W_add_2_i32_i32
    int y = add(10, 20, 30); // calls _W_add_3_i32_i32_i32
    return x + y;
}

5.6 References (&) & Pointers (*)

Pass-by-reference allows in-place mutation of caller arguments without manual address-of (&) and dereferencing (*) syntax at each call site. 

void swap(int& a, int& b) {
    int tmp = a;
    a = b;
    b = tmp;
}

int main() {
    int x = 1;
    int y = 2;
    swap(x, y);
    return x; // 2
}

5.7 Control Flow

Standard control flow constructs are supported: if, else, while, for, break, continue, and return. 

int compute(int n) {
    int sum = 0;
    for (int i = 0; i < n; i = i + 1) {
        if (i % 2 == 0) {
            sum = sum + i;
        }
    }
    return sum;
}

6. Architecture & IR

The compiler executes in discrete sequential stages without cyclic dependencies:

  1. Lexical Analysis (src/lexer.c): Scans UTF-8 input, interned identifiers, numeric constants, and operators.
  2. Parsing (src/parser.c): Recursive descent parser with operator precedence expression evaluation producing an Abstract Syntax Tree.
  3. Semantic Analysis (src/sema.c): Type checking, member offset layout calculation, symbol scoping, and method name mangling.
  4. IR Generation (src/ir.c): Translation of AST to linear 3-address code intermediate representation with explicit typed operations.
  5. Optimization (src/opt.c): Constant folding and redundant jump elimination passes.
  6. Code Generation (src/codegen_x86.c): System V AMD64 assembly output generation with 16-byte aligned stack allocation.

Intermediate Representation Example

Given the C++ function:

int calc(int a, int b) {
    return a * b + 7;
}

winds emits the following linear 3AC IR (visible via --emit-ir):

function _W_calc(a: i32, b: i32) -> i32:
    t0 = mul.i32 a, b
    t1 = add.i32 t0, 7
    ret.i32 t1

And generates the following x86_64 GNU assembly (visible via -S):

    .globl  _W_calc
    .type   _W_calc, @function
_W_calc:
    pushq   %rbp
    movq    %rsp, %rbp
    movl    %edi, -4(%rbp)
    movl    %esi, -8(%rbp)
    movl    -4(%rbp), %eax
    imull   -8(%rbp), %eax
    addl    $7, %eax
    movq    %rbp, %rsp
    popq    %rbp
    ret

7. Frequently Asked Questions

Why build a C++ compiler without LLVM?

LLVM is large and complex. A basic LLVM toolchain easily exceeds 150 MB of disk space and adds significant startup and link overhead. winds demonstrates that a standalone, self-contained compiler written in standard C can compile C++ code in 0.3 ms with a 325 KB executable.

How does winds achieve sub-millisecond compilation?

Three key architectural factors contribute to this latency:

  • Contiguous chunked arena allocators avoid thousands of fine-grained malloc/free calls.
  • FNV-1a string interning turns string lookups into simple pointer comparisons.
  • Linear single-pass 3AC IR generation lowers directly into x86_64 instructions without traversing complex heavyweight graph structures.
Can winds call standard C library functions?

Yes. Because winds strictly adheres to the System V AMD64 ABI calling convention (passing arguments in %rdi, %rsi, %rdx, %rcx, %r8, %r9), code compiled with winds can declare and link against standard libc functions such as malloc, free, printf, or exit.

How does winds manage RAII object destruction?

The semantic analyzer records local variables with non-trivial destructors within each lexical scope block. When an exit path (such as end of scope or return) is reached, destructor calls for all active instances in that scope are emitted in reverse order of declaration.

How are overloaded functions resolved?

The semantic analyzer matches call sites by matching the callee identifier against candidate overloads, checking argument counts and parameter types. Object code symbols are mangled with unique type suffixes to avoid link conflicts.

What platforms are currently supported?

winds currently targets Linux x86_64 (AMD64) using the standard GNU assembler (as) and GNU linker (ld or gcc).
